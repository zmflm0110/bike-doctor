# 선행 연구·새 기술과 비교 (2026-09-30)

> 한 줄 요약: "짧게 빌렸다 같은 대여소에 반납한 기록 = 고장 신호" 자체는 알려진 생각이다. RIDEY 의 차이는
> **정답(고장 목록)도 GPS 도 없이, 누구나 받는 공개 실시간 API 만으로, '서로 다른 사람' 연쇄를 5분마다 계산하고 스스로 채점한다**는 것.
> 새 기술을 다 붙여 보기보다, 실제 기록으로 재서 이기는 것만 쓴다.

## 2. 새 기술을 우리 문제에 대 보면

| 기술 | 무엇 | 우리에게 | 판단 |
|---|---|---|---|
| 그래디언트 부스팅 (작게) | 나무 여러 그루 | 실시간 목록 +3%p 안팎, 두 달 모두, 확률도 실제와 맞음(아래 3-1) | **쓸 만함** — 60그루·깊이 3 이면 SQL 로 옮길 크기 |
| [TabPFN v2/2.5 (*Nature* 2025)](https://www.nature.com/articles/s41586-024-08328-6) | 표 자료용 기초 모델, 학습 없이 예측 | 1만~5만 건에서 강함. 우리는 10만 건+, DB 안에서 돌릴 수 없음 | 이득 작음 |
| [컨포멀 예측](https://arxiv.org/pdf/2512.23602) | 오류율을 **수학적으로 보장**하는 임계값 | "이 목록의 최소 N% 는 다음 사람도 반납" 을 보장해 정비 기사에게 보여 줄 수 있음 | 가볍고 억지 아님 — 후보 |
| [PostgresML](https://postgresml.org/) | DB 안 머신러닝 확장 | Supabase 에서 못 씀 | 대신 나무를 SQL 로 바꾸면 됨([sqlgbm](https://github.com/mattismegevand/sqlgbm) 같은 방식) |
| GNN·트랜스포머 | 대여소 그래프·궤적 학습 | 정답·GPS 가 없어 학습 신호가 약함 | 억지 |
| [기기 안 글자 인식 (Apple Vision)](https://developer.apple.com/documentation/vision/vnrecognizetextrequest) | 카메라로 자전거 번호 읽기 | 대여소에서 "어느 자전거?" 에 필요. 실제 번호판이 읽히는지 현장 확인 필요 | 현장 사진으로 먼저 시험 |

## 3. 우리 자료로 잰 것 (서울 2026년 1·3월로 배우고 6월로 시험, 같은 수를 고를 때 정밀도)

### 3-1. 작은 부스팅 (나무 60그루·깊이 3, 마디 866개)
| 시험 | 규칙 | 작은 부스팅 | 차이 95% 범위 |
|---|---:|---:|---|
| 1·3월 → 6월 | 49.1% | 52.8% | +3.0 \~ +4.4%p |
| 1월 → 3월 | 48.9% | 51.9% | +2.3 \~ +3.8%p |

확률이 실제와 맞는가(6월, 규칙 목록 안): 모델이 25.8% 라 한 묶음 → 실제 22.6%, 34.5% → 33.3%, 55.2% → 53.1%, 75.1% → 74.1%, 82.8% → 83.9%.
(큰 모델 400그루는 3월 시험에서 오히려 +0.5\~2.4%p 로 작았다 — 작은 모델이 더 안정적.) 자세한 비교: [ml_compare.md](ml_compare.md).

### 3-2. 외면 신호 (Kaspi 2016 의 생각을 우리 자료로)
정상 반납 뒤 같은 대여소에서 다른 자전거가 k번 빌려 가는 동안 혼자 남은 자전거:

| k | 3월 다음 헛대여 | 6월 다음 헛대여 | 3월 그사이 고장신고 | 6월 그사이 고장신고 |
|---|---:|---:|---:|---:|
| 0 | 2.13% | 2.01% | 0.01% | 0.01% |
| 21\~40 | 3.04% | 2.86% | 0.17% | 0.16% |
| 81\~160 | 4.14% | 3.91% | 0.52% | 0.51% |
| 160+ | 6.04% | 5.64% | 1.23% | 1.14% |

→ 신호는 두 달 모두 뚜렷하다(신고 비율 약 100배). 혼자선 약하니(최대 6%) **연쇄 신호에 더해** 쓴다. 트럭 재배치는 기록에 없어서, 다음 대여가 같은 대여소에서 시작한 경우만 셌다.

자체 모델(5특징)에 외면 수를 특징으로 더해 봤더니(2026-10-01) 같은 수를 고를 때 +0.19 / +0.43 / +0.11%p (6월·3월·1월 시험, 95% 범위가 대부분 0 을 포함) — 연쇄·지난 7일 헛대여 수가 이미 같은 정보를 담고 있다. **넣지 않는다.**

### 3-3. 2상태 건강 모델 (HMM 필터, 숫자 6개를 정답 없이 가능도로 맞춤)
| 시험 | 규칙 | 건강 모델 | 전체 순위 AUC (규칙 / 건강 / 부스팅) |
|---|---:|---:|---|
| 1·3월 → 6월 | 49.1% | 49.4% | 0.684 / 0.764 / 0.778 |
| 1월 → 3월 | 48.9% | 47.9% | 0.676 / 0.754 / 0.774 |

→ 순위는 규칙보다 훨씬 잘 매기지만, 같은 수를 고르면 이득이 없고 확률이 실제보다 낮게 나왔다(맞춘 값: 고장이면 헛대여 33%). "가끔 말썽" 과 "완전히 망가짐" 을 한 상태로 묶어서다 → 3상태가 필요. **지금은 쓰지 않는다.**

### 3-4. 실시간 채점 (2026-09-27 10:20 \~ 09-30 21:20)
경보 뒤 처음 빌린 다른 사람 1,215명 중 382명(31.4%)이 또 바로 반납 — 지난 기록으로 같은 방식 32\~34% 와 같다. 평소 2.5%.

## 4. 코드 점검에서 나온 것
- 서버(`server/app.py`)는 입력을 정규식으로 검사하고 SQL 은 매개변수로만 쓴다 — 문제없음.
- ~~클라우드 DB 의 '사람 확인' 은 누구나 제한 없이 넣을 수 있다~~ → **고침(2026-10-01)**: 표마다 같은 자전거 10분에 3번, 전체 1분에 20번·1시간에 300번(`supabase/schema.sql` 의 `live.limit_inserts`). 개인정보(IP)는 남기지 않는다.
- 5분 작업: 하루 288번 모두 성공, 평균 34초(한도 120초). 한 연결의 첫 조회가 느린 것(수 초)이 대부분 — 무료 요금제 DB 의 캐시 사정이라 값이 크게 흔들린다.
- 같은 엔진이 파이썬·SQL·스위프트·자바스크립트 네 곳에 있고, 서로 같은 답을 내는지 자동 검사한다(`tools/supabase_live_load.py --parity`, `tests/web/parity_fixture.js`).
